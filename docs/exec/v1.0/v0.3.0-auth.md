# v0.3.0 — Authentifizierung und Berechtigungen

## Ziel

Nur du kommst ins Dashboard. Jede Route prüft serverseitig, und die Prüfung
läuft über einen einzigen Mechanismus, den Web und Bot gemeinsam nutzen.

## Voraussetzungen

- `v0.2.0` abgenommen
- OAuth-Anwendung bei Discord konfiguriert, Redirect-URI eingetragen

**Dieser Abschnitt ist ASVS-Level-2-Bereich.** `docs/security-baseline.md` ist
vor Beginn zu lesen und am Ende durchzugehen.

## Umfang

### OAuth-Flow

- Login-Route erzeugt `state`, legt ihn serverseitig ab und leitet zu Discord
- Callback validiert `state`, tauscht Code gegen Token, holt Nutzerprofil
- Redirect-URI wird gegen eine Allowlist geprüft, niemals aus der Anfrage
  übernommen
- Bei Fehlern von Discord: `fail closed`, kein unauthentifizierter Fallback
- Entscheidung dokumentieren: werden Discord-Tokens persistiert? Falls ja,
  verschlüsselt — falls nein, nach dem Login verwerfen

### Sessions

- Serverseitige Sessions, Cookie mit `HttpOnly`, `Secure`, `SameSite=Lax`
- Session-ID kryptografisch zufällig
- **Rotation nach erfolgreichem Login** (Session Fixation)
- Logout invalidiert serverseitig, nicht nur das Cookie
- Idle- und Absolut-Timeout definiert und durchgesetzt

### Nutzer und Rollen

- `User`-Modell: Discord-ID (`BigInteger`), Anzeigename, Avatar, Zeitstempel
- App-Rollen `owner`, `admin`, `moderator`, `member`
- Mapping Discord-Rolle → App-Rolle, plus explizite Overrides pro Nutzer
- Owner wird über Konfiguration festgelegt, nicht über die Datenbank

### Permissions

- `core/permissions.py`: Action-Enum, gespeist aus den `permissions.py` der
  Module
- `can(user, guild, action) -> bool` — **die** Prüffunktion
- Deny by default: unbekannte Action, unbekannte Rolle oder fehlender
  Guild-Kontext ergeben `False`
- `web/deps.py`: Dependency `require(action)`
- `bot/base.py`: Cog-Check, der dieselbe Funktion nutzt
- Guild-Scoping ist Teil jeder Prüfung

### Developer-Mode

- Eigene Berechtigung, nicht nur ein Konfigurations-Flag
- Sichtbarmachen von Debug-Feldern, Registry-Inhalt, Statusdetails
- Design-Harness unter `/design` an diese Berechtigung binden
- Terminal aus `v0.2.0` wird jetzt berechtigungspflichtig

### Sicherheitslogging

- Protokolliert werden: Login, Logout, fehlgeschlagene Autorisierung,
  Rollenänderung
- Keine Tokens, Session-IDs oder vollständigen Profildaten im Log

### Tests

Verbindlich, aus der Baseline:

- Nicht angemeldeter Zugriff auf geschützte Route → Redirect bzw. 401
- Angemeldet ohne Berechtigung → 403
- Zugriff auf Objekt einer **fremden Guild** scheitert bei korrekter ID
- Callback mit fehlendem oder falschem `state` scheitert
- Session-ID nach Login unterscheidet sich von der vorherigen
- Logout macht die alte Session unbrauchbar
- Route ohne Auth-Dependency wird erkannt (Deny by default)

## Abnahmekriterien

- [ ] Login über Discord funktioniert, Logout ebenfalls
- [ ] Alle bestehenden Routen sind geschützt; Terminal und `/design` sind ohne
      Berechtigung nicht erreichbar
- [ ] Alle oben genannten negativen Tests grün
- [ ] Cookie-Flags im Browser überprüft
- [ ] Kein Token und keine Session-ID im Log auffindbar
- [ ] Durchgang durch `docs/security-baseline.md` dokumentiert

## Nicht in diesem Abschnitt

- Guild-Synchronisation aus Discord (kommt in `v0.4.0`)
- Einstellungsverwaltung
- Rate Limiting — bewusst offen, Entscheidung in `v0.7.0`
- Fachliche Module

## Fußangeln

**`state` vergessen** macht den Login CSRF-anfällig. Er muss serverseitig
gespeichert und nach Gebrauch entfernt werden.

**Session-Rotation vergessen** ist die häufigste Lücke in selbstgebauter Auth.

**Berechtigung nur im Template geprüft.** Ein ausgeblendeter Button ist kein
Schutz — die Route muss unabhängig davon prüfen.

**Owner in der Datenbank.** Wenn der Owner aus derselben Tabelle kommt, die er
verwaltet, kannst du dich selbst aussperren. Er gehört in die Konfiguration.

**Rollenprüfung direkt gegen Discord** im Cog. Umgeht das Modell und ist im Web
nicht reproduzierbar.

**Geheimnisvergleiche mit `==`.** `secrets.compare_digest` verwenden.

# v0.10.0 — Härtung und Freigabe

Vorletzter Abschnitt vor `v1.0.0`. Die Nummer verschiebt sich, weil die vier
Module aus `v0.6.0-modules.md` je einen eigenen Minor-Tag erhalten.

## Ziel

Kein neues Feature. Das Vorhandene wird betriebsfest: Datensicherung, die
nachweislich funktioniert, Dokumentation, die zum Code passt, und ein
vollständiger Durchgang durch die Sicherheits-Baseline.

## Voraussetzungen

- Alle Feature-Module abgenommen
- Das System läuft seit mindestens zwei Wochen auf Fuchs

## Umfang

### Datensicherung

- `VACUUM INTO` per Cron auf Fuchs, unabhängig vom Deploy-Backup
- Aufbewahrungsfrist und Rotation festgelegt
- **Wiederherstellung mindestens einmal geprobt** — ein Backup, das nie
  eingespielt wurde, ist eine Vermutung
- Litestream prüfen und entscheiden; Entscheidung als ADR festhalten
- Ablage der Sicherungen außerhalb von Fuchs erwägen

### Betriebsfestigkeit

- Rate Limiting entscheiden und umsetzen: Login und schreibende Endpunkte
- Verschlüsselung gespeicherter Discord-Tokens entscheiden und umsetzen, samt
  Schlüsselverwaltung — beides steht als offener Punkt in der Baseline
- Retention für Logeinträge durchgesetzt und geprüft
- Verhalten bei vollem Datenträger geprüft
- Health-Check prüft nicht nur den Prozess, sondern auch Datenbank und
  Bot-Status
- Neustartverhalten nach Absturz und nach Serverneustart geprüft

### Sicherheit

- Vollständiger Durchgang durch `docs/security-baseline.md`, dokumentiert
- Alle CodeQL-Befunde bewertet
- Abhängigkeiten aktuell, keine offenen Warnungen
- Rechte auf `/srv/teabot` und `/srv/github-actions` überprüft
- `SECURITY.md` auf Aktualität geprüft, Private Vulnerability Reporting aktiv

### Dokumentation

- `README.md`: Zweck, Funktionsumfang, Installationsanleitung, Screenshots
- Alle Bereichs-READMEs gegen den tatsächlichen Code geprüft — Abweichungen
  sind laut `ARCHITECTURE.md` Bugs
- ADRs für alle in diesem Verlauf getroffenen Entscheidungen nachgezogen
- `.env.example` vollständig
- Fehlende ADRs: Settings-Serialisierung, Token-Speicherung, Backup-Verfahren

### Tests

- Testabdeckung gesichtet: nicht auf Quote, sondern auf Lücken bei
  Berechtigungen und Guild-Scoping
- End-to-End: Prozess startet, Bot verbindet, `/health` grün, Login möglich
- Migrationskette von leer bis `head` in CI belegt
- Wiederherstellung aus Backup als dokumentierte Prozedur, nicht als Test

## Abnahmekriterien

- [ ] Wiederherstellung aus einem Backup erfolgreich durchgeführt
- [ ] Baseline-Durchgang vollständig, Abweichungen entweder behoben oder als
      bewusstes Restrisiko dokumentiert
- [ ] Keine offenen kritischen CodeQL- oder Dependabot-Befunde
- [ ] Alle READMEs deckungsgleich mit dem Code
- [ ] Rate Limiting aktiv
- [ ] Token-Speicherung entschieden und umgesetzt
- [ ] `README.md` erlaubt einer fremden Person die Installation
- [ ] System läuft zwei Wochen ohne unerklärten Neustart

## Nicht in diesem Abschnitt

- Neue Features jeder Art
- Refactorings ohne konkreten Befund
- Performance-Optimierung ohne gemessenes Problem

## Danach: `v1.0.0`

Kein eigener Abschnitt. Der Tag wird gesetzt, wenn dieser Abschnitt abgenommen
ist und der Stand als Pre-release einige Tage auf Fuchs lief. Release als
*Latest* markieren.

Für v2.0 vorgemerkt: LLM-gestützte Bot-Antworten, Statistiken, Scheduler,
mehrere Bot-Clients, Outbox für Gateway-Zustellung bei Bot-Ausfall.

## Fußangeln

**Ungeprobte Wiederherstellung.** Der häufigste Fehler in Selbstbetrieb — das
Backup läuft jahrelang und ist im Ernstfall unbrauchbar.

**Härtung als Aufräumphase missverstehen.** Sie ist kein Puffer für
Restfeatures. Was noch fehlt, verschiebt sich nach v1.0.

**Baseline-Durchgang als Formalie.** Der Wert liegt darin, jede Anforderung
gegen den echten Code zu prüfen — nicht gegen die Erinnerung daran.

**Dokumentation zum Schluss.** Ist an dieser Stelle bereits veraltet. Der
Durchgang deckt Abweichungen auf, ersetzt aber kein Mitschreiben unterwegs.

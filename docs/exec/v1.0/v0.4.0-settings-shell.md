# v0.4.0 — Settings-Framework und Admin-Shell

## Ziel

Das Gerüst, in dem alle folgenden Module wohnen: Navigation entsteht aus der
Registry, Einstellungsseiten entstehen aus deklarierten Schemata. Nach diesem
Abschnitt kostet ein neues Modul keine Handarbeit am Rahmen mehr.

**Dieser Abschnitt muss vor `v0.5.0` fertig sein.** Sonst wird jede
Einstellungsseite von Hand gebaut, und die Nacharbeit trifft jedes bereits
existierende Modul.

## Voraussetzungen

- `v0.3.0` abgenommen
- Der `MODULE`-Deskriptor ist entschieden (siehe Fußangeln)

## Umfang

### Guild-Synchronisation

- `Guild`-Modell: Discord-ID, Name, Icon, `active`, Zeitstempel
- Synchronisation beim Bot-Start und über einen Listener bei Beitritt/Verlassen
- Rollen der Guild werden mitgeführt, damit das Rollen-Mapping aus `v0.3.0`
  konfigurierbar wird
- Guild-Auswahl im Dashboard, wenn mehr als eine vorhanden ist

### Settings-Framework

- Store: `(guild_id, module, key) -> value`, ein Eintrag pro Kombination
- Schema-Deklaration je Modul: Typ, Default, Label, Hilfetext, Gruppe,
  Sichtbarkeit, `dev_only`, Validierung
- Unterstützte Typen mindestens: `bool`, `int`, `str`, `select`,
  `channel`, `role`, `multi_select`
- Typisierter Accessor mit Cache; Invalidierung bei Schreibzugriff
- Defaults kommen aus dem Schema, nicht aus der Datenbank — ein fehlender
  Eintrag ist kein Fehler
- Schreibzugriff erfordert eine Berechtigung und wird ins Sicherheitslog
  geschrieben
- Generischer Renderer: eine Einstellungsseite pro Modul, vollständig aus dem
  Schema erzeugt

### Admin-Shell

- `base.html` mit Kopfzeile, Guild-Auswahl, Navigation, Nutzermenü
- Navigation entsteht aus den `MODULE`-Deskriptoren, gefiltert nach
  Berechtigung und Aktivierungszustand
- Modul-Aktivierung pro Guild, verwaltet über das Settings-Framework
- Fehlerseiten für 401, 403, 404, 500
- Startseite: Bot-Status, letzte Logeinträge, Kennzahlen
- Harness-Einträge für Formularfelder aller Settings-Typen, Navigation und
  leere Zustände

### Tests

- Accessor liefert Default, wenn kein Eintrag existiert
- Schreibzugriff invalidiert den Cache
- Einstellung einer Guild ist in einer anderen Guild nicht sichtbar
- Schreibzugriff ohne Berechtigung → 403
- Navigation enthält kein Modul, für das die Berechtigung fehlt
- Deaktiviertes Modul ist nicht erreichbar, auch nicht über direkte URL
- Ungültiger Wert wird gegen das Schema abgelehnt

## Abnahmekriterien

- [ ] Ein Modul mit deklariertem Schema erhält **ohne** eigenen Template-Code
      eine funktionierende Einstellungsseite
- [ ] Navigation zeigt genau die Module, für die Berechtigung besteht
- [ ] Deaktiviertes Modul ist per URL nicht erreichbar
- [ ] Guild-Trennung durch Test belegt
- [ ] Alle Settings-Typen sind in der Harness sichtbar
- [ ] Änderung einer Einstellung erscheint im Sicherheitslog

## Nicht in diesem Abschnitt

- Fachliche Module
- Einstellungshistorie oder Rollback
- Import/Export von Konfiguration
- Mehrsprachigkeit

## Fußangeln

**Der `MODULE`-Deskriptor muss vorher entschieden sein.** Registry und
Navigation programmieren dagegen. Mindestfelder: technischer Name,
Anzeigename, Icon, URL-Prefix, benötigte Berechtigung zur Anzeige,
Abhängigkeiten, ob deaktivierbar. Nachträgliche Erweiterung ist möglich, eine
Umbenennung nicht ohne Anpassung aller Module.

**Werte typisiert speichern.** Alles als String abzulegen und beim Lesen zu
konvertieren führt zu stillen Fehlern bei Booleans. Serialisierung explizit
festlegen und im Accessor durchsetzen.

**Cache ohne Invalidierung** ist die klassische Falle: die Einstellung wird
gespeichert, wirkt aber erst nach Neustart.

**Defaults in die Datenbank schreiben.** Dann lässt sich ein Default später
nicht mehr ändern, ohne Bestandsdaten anzufassen. Defaults bleiben im Schema.

**Navigation aus einer festen Liste.** Widerspricht der Registry und wird beim
nächsten Modul vergessen.

# v0.5.0 — Tickets als Referenzmodul

## Ziel

Das erste fachliche Modul — und damit der Beweis, dass das Slice-Muster
funktioniert. Tickets sind bewusst gewählt: sie berühren Discord-Interaktion,
Web-UI, Zustandslogik und Berechtigungen. Was hier hakt, hakt bei jedem
weiteren Modul.

Dieses Modul ist ab dann die **Vorlage**. Nachfolgende Module orientieren sich
an seiner Struktur, nicht an einer Beschreibung davon.

## Voraussetzungen

- `v0.4.0` abgenommen — insbesondere das Settings-Framework

## Umfang

### Datenmodell

- `Ticket`: `guild_id`, laufende Nummer je Guild, Ersteller, Betreff, Status,
  Kanal-ID, Zeitstempel für Erstellung, Zuweisung, Schließung
- `TicketMessage` oder Verweis auf den Discord-Kanal — Entscheidung
  dokumentieren
- Status als Enum: `open`, `assigned`, `closed`
- Migration mit sinnvoller `downgrade()`

### Service

Invarianten, die **ausschließlich** hier leben:

- Ticket kann nur erstellt werden, wenn das Modul für die Guild aktiv ist
- Obergrenze offener Tickets pro Nutzer (Einstellung)
- Schließen nur durch Ersteller oder Moderator
- Ein geschlossenes Ticket kann nicht erneut geschlossen werden
- Zuweisung nur an Nutzer mit Moderator-Rolle
- Laufende Nummer ist pro Guild eindeutig und lückenlos

Fehler als Domain-Exceptions in `modules/tickets/exceptions.py`, abgeleitet aus
`core/exceptions/`.

### Berechtigungen

`tickets.create`, `tickets.view_own`, `tickets.view_all`, `tickets.assign`,
`tickets.close`, `tickets.configure`

### Einstellungen

Kategorie-Kanal für Ticket-Kanäle, Moderator-Rolle, Obergrenze offener Tickets,
Begrüßungstext, ob Transkript beim Schließen gespeichert wird

### Adapter

- `cog.py`: `/ticket new`, `/ticket close`, `/ticket assign`; Erstellung legt
  einen Kanal an und setzt Rechte
- `router.py`: Übersicht mit Filter, Detailansicht, Zuweisen, Schließen —
  Fragmente für Alpine
- Beide rufen **denselben** Service; keine Logik im Adapter

### Web-Aktion nach Discord

Schließen im Dashboard muss den Discord-Kanal archivieren oder löschen. Das
läuft über das `BotGateway`. Ist der Bot offline, wirft das Gateway
`BotUnavailable`, und das UI zeigt einen verständlichen Fehler — der
Datenbankzustand bleibt konsistent.

### Templates und Harness

Übersicht, Detailansicht, Statusabzeichen; Harness-Einträge für leere Liste,
langen Betreff, alle Statuswerte, fehlenden Avatar

### Tests

- Service-Tests **ohne** Discord-Mock und **ohne** HTTP-Client — das ist der
  Lackmustest für die Schichtung
- Jede Invariante hat einen negativen Test
- Zugriff auf ein Ticket einer fremden Guild scheitert
- `tickets.view_own` sieht fremde Tickets nicht
- Schließen ohne Berechtigung → 403
- Gateway-Ausfall führt zu verständlichem Fehler ohne inkonsistente Daten
- Slash-Command und Web-Route erzeugen identische Ergebnisse

## Abnahmekriterien

- [ ] Ticket per Slash-Command und per Dashboard erstellbar, mit identischem
      Ergebnis
- [ ] Alle Invarianten durch negative Tests belegt
- [ ] Service-Tests laufen ohne Discord- und HTTP-Attrappen
- [ ] Einstellungsseite entstand ohne eigenen Template-Code
- [ ] Modul lässt sich für eine Guild deaktivieren; Commands sind dann inaktiv
- [ ] Kein Import aus einem anderen Modul
- [ ] CodeRabbit meldet keine Schichtverletzung
- [ ] Bot offline: Schließen im UI scheitert verständlich, Daten bleiben
      konsistent

## Nicht in diesem Abschnitt

- Transkript-Export als Datei
- Ticket-Kategorien oder Formulare
- Automatische Schließung nach Inaktivität
- Statistiken

## Fußangeln

**Logik im Cog** ist hier besonders verlockend, weil der Command-Handler den
Kanal direkt zur Hand hat. Genau das ist die Verletzung, die dieses Modul
verhindern soll.

**Kanalanlage und Datenbankeintrag** sind zwei Operationen ohne gemeinsame
Transaktion. Reihenfolge festlegen und den Fehlerfall behandeln: Was gilt, wenn
der Kanal existiert, aber der Commit scheitert? Empfehlung: erst Datensatz, dann
Kanal, Kanal-ID nachtragen.

**Laufende Nummer unter Gleichzeitigkeit.** `MAX(number) + 1` ist bei zwei
gleichzeitigen Anfragen falsch. Über einen Zähler pro Guild mit
Datenbank-Constraint lösen, nicht durch Nachzählen.

**Ticket-Kanal-Rechte.** Wer darf lesen? Falsch gesetzte Overwrites sind ein
Datenleck innerhalb des Servers.

**Modul deaktiviert, Command noch da.** Slash-Commands sind global registriert
— der Check auf Modulaktivierung muss im Command selbst erfolgen.

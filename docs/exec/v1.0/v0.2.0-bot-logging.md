# v0.2.0 — Bot und Logging

## Ziel

Der Bot geht online, lässt sich starten, stoppen und neu starten, und du siehst
im Browser live, was er tut.

## Voraussetzungen

- `v0.1.0` abgenommen
- Discord-Anwendung angelegt, Bot-Token vorhanden, Bot auf einem Testserver

## Umfang

### Client

- `bot/client.py`: Factory, die eine frische `TeaBot`-Instanz baut; Intents
  explizit und minimal
- `bot/base.py`: `BaseCog` mit gemeinsamem Logger und Fehlerbehandlung
- `bot/gateway.py`: Implementierung des `BotGateway`-Protokolls, wirft
  `BotUnavailable`, wenn der Client nicht bereit ist

### Lifecycle

- `bot/manager.py`: `start()`, `stop()`, `restart()`, `status()`
- `asyncio.Lock` um alle Operationen
- Done-Callback, der Exceptions loggt und Status auf `crashed` setzt
- Status-Enum: `stopped`, `starting`, `ready`, `stopping`, `crashed`
- Lifespan in `app/` startet den Bot, wenn Autostart konfiguriert ist
- Shutdown: erst Bot, dann Engine

### Logging

- Logger-Baum nach `__name__`; `discord`-Logger auf `WARNING`
- `core/logbus.py`: Ringpuffer plus `asyncio.Queue` je verbundenem Client
- `logging.Handler`, der **strukturierte Objekte** in den Bus schreibt
  (Zeitstempel, Level, Logger-Name, Nachricht, optional Guild) — keine rohen
  ANSI-Sequenzen
- Persistente Logeinträge in der Datenbank für fachlich relevante Ereignisse,
  mit Retention

### Terminal-Oberfläche

- SSE-Endpunkt, der den Logstream ausliefert
- Terminal-Komponente: Alpine mit `EventSource`, Auto-Reconnect,
  Level-Filter, Pause/Fortsetzen, Begrenzung der Zeilen im DOM
- Level-Zuordnung auf CSS-Klassen clientseitig aus dem isolierten
  Terminal-Farbsatz
- Bot-Steuerung im UI: Start, Stop, Restart, Statusanzeige
- Harness-Einträge für Terminal und Statusanzeige in allen Zuständen

### Tests

- Manager: Restart erzeugt eine neue Instanz; Doppelstart wird verhindert;
  Task-Exception führt zu Status `crashed`
- Log-Bus: mehrere Abnehmer erhalten Einträge; ein langsamer Abnehmer bremst
  die Anwendung nicht
- Gateway: wirft `BotUnavailable`, wenn der Client fehlt
- Router: SSE-Endpunkt liefert `text/event-stream`

## Abnahmekriterien

- [ ] Bot erscheint auf dem Testserver online
- [ ] Restart über das UI erzeugt eine neue funktionsfähige Client-Instanz
- [ ] Eine im Cog geworfene Exception erscheint im Terminal und setzt den Status
      auf `crashed`, statt lautlos zu verschwinden
- [ ] Terminal zeigt Einträge live, verbindet nach Netzunterbrechung neu
- [ ] Bot lässt sich stoppen, ohne dass die Weboberfläche ausfällt
- [ ] `docker compose down` beendet innerhalb von zwei Sekunden ohne Traceback
- [ ] Kein Token in irgendeiner Logzeile

## Nicht in diesem Abschnitt

- Authentifizierung — das Terminal ist noch ungeschützt und **darf deshalb
  nicht öffentlich erreichbar sein**
- Slash-Commands mit Fachlichkeit
- Mehrere Clients oder Versionen
- Berechtigungen

## Fußangeln

**Stiller Task-Tod.** Ohne Done-Callback verschwindet eine Exception im Task
spurlos, und die Statusanzeige lügt. Das ist der wichtigste Punkt dieses
Abschnitts.

**Client-Wiederverwendung.** Ein geschlossener `discord.Client` lässt sich nicht
erneut starten. Restart heißt: neue Instanz aus der Factory, Cogs neu laden.

**`bot.run()`** blockiert den Event Loop und damit den Webserver. Nur
`await bot.start()` in einem Task.

**Unbegrenztes Queue-Wachstum.** Ein Abnehmer, der nicht liest, lässt die Queue
volllaufen. Größe begrenzen und bei Überlauf verwerfen statt blockieren.

**DOM-Wachstum im Terminal.** Ohne Obergrenze wird die Seite nach Stunden
unbenutzbar.

**Rohes ANSI über SSE** ist eine Sackgasse — strukturierte Objekte senden und
clientseitig auf Klassen abbilden.
